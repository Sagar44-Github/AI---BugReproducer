What to VerifyThe frameworkHint on initial pipeline run. When a stored preferredFramework exists in localStorage, it's sent as frameworkHint in the /run request body. Verify this actually reaches the Test Writer agent prompt and not just the route handler. Trace: localStorage → request body → runBugReproductionPipeline(frameworkHint) → Test Writer prompt injection. If the hint is parsed from the body but not forwarded to the pipeline function, the preference silently has no effect on initial runs — only on regeneration.The regenerate endpoint on an analysis that's not completed. The endpoint validates status === 'completed' before running. Verify the error response for a non-completed analysis is a clean JSON error, not a raw exception. The response should be something like { error: "Analysis must be completed before regenerating test code" } with a 400 status — not a 500 with a stack trace.The syntax validator runs on the regenerated output. The runTestWriterWithOverride function calls the Test Writer and then the syntax validator. Verify the testSyntaxStatus saved back to the DB reflects the validator result — not just the Test Writer output. If the validator is called but its result isn't persisted, the badge on the Test Code tab will be stale after regeneration.The dropdown pre-population timing. preferredFramework is read from localStorage on mount. If the analysis is still loading when the component mounts, the dropdown might render before the detected framework pill appears — creating a brief flash where the dropdown shows a preference but no detection context. Verify the dropdown and the detection pill load in a consistent order, ideally both appearing after the analysis data is available.JUnit and RSpec regeneration. These two frameworks are in the dropdown but may not have explicit syntax validators — the syntaxValidator.ts covers Python, JS/TS, and Postman. Verify that regenerating with JUnit or RSpec returns unchecked status rather than a false warning. If the validator attempts to parse Java or Ruby as another language type it'll produce incorrect results.One Check for the DemoSet preferredFramework to pytest in localStorage manually or by making one successful regeneration. Then submit a new bug report through the full pipeline. Verify:
The initial /run request body includes frameworkHint: "pytest"

That last point — the audit trail distinguishing between detected and overridden framework — is worth adding if it's not already there. A judge reading the audit trail should be able to tell whether the framework was auto-detected or user-specified. One extra detail row in the Test Writer audit entry: { label: "framework source", value: "user override", status: "info" } vs { label: "framework source", value: "auto-detected", status: "ok" }.
