# Database

## Overview

The database is a single PostgreSQL instance accessed via Drizzle ORM. The schema is defined in `lib/db/src/schema/analyses.ts` and exported from `lib/db/src/index.ts`.

**Connection**: via `DATABASE_URL` environment variable  
**ORM**: Drizzle ORM (`drizzle-orm` + `drizzle-kit`)  
**Schema push**: `pnpm --filter @workspace/db run push` (dev-only, no migration files)

---

## Tables

### `projects`

Organises analyses into logical groups. Each project can have Slack/Discord webhook URLs for pipeline completion notifications.

| Column | Type | Nullable | Default | Description |
|--------|------|----------|---------|-------------|
| `id` | `serial` (integer) | No | auto-increment | Primary key |
| `name` | `text` | No | — | Display name of the project |
| `description` | `text` | Yes | NULL | Optional description |
| `default_framework` | `text` | Yes | NULL | Default test framework for analyses in this project (e.g. `"Jest"`, `"Pytest"`) |
| `slack_webhook_url` | `text` | Yes | NULL | Slack incoming webhook URL for pipeline completion notifications |
| `discord_webhook_url` | `text` | Yes | NULL | Discord webhook URL for pipeline completion notifications |
| `created_at` | `timestamp` | No | `NOW()` | Creation timestamp |
| `updated_at` | `timestamp` | No | `NOW()` | Last modification timestamp |

**Drizzle type**: `typeof projectsTable.$inferSelect` → exported as `Project`  
**Insert schema**: `insertProjectSchema` (auto-generated by `drizzle-zod`, omits `id`, `created_at`, `updated_at`)

### `api_keys`

Stores hashed API keys for programmatic access to the pipeline via `POST /api/webhook/analyze` (CI/CD integration). The actual key is never stored — only a hash and a display prefix.

| Column | Type | Nullable | Default | Description |
|--------|------|----------|---------|-------------|
| `id` | `serial` (integer) | No | auto-increment | Primary key |
| `name` | `text` | No | — | Human-readable label (e.g. `"CI/CD - GitHub Actions"`) |
| `key_hash` | `text` | No | — | SHA-256 hash of the full API key |
| `prefix` | `text` | No | — | First 8 characters of the key for display (e.g. `"brk_a1b2"`) |
| `note` | `text` | Yes | NULL | Optional usage note |
| `project_id` | `integer` | Yes | NULL | Optional FK to `projects.id` |
| `is_active` | `boolean` | No | `true` | Whether the key is currently valid |
| `created_at` | `timestamp` | No | `NOW()` | Creation timestamp |
| `last_used_at` | `timestamp` | Yes | NULL | Updated on each successful API call |

**Drizzle type**: `typeof apiKeysTable.$inferSelect` → exported as `ApiKey`

### `analyses`

The core table. Each row represents one bug report submission and its complete pipeline results.

#### Identity & Input

| Column | Type | Nullable | Default | Description |
|--------|------|----------|---------|-------------|
| `id` | `serial` | No | auto-increment | Primary key |
| `title` | `text` | No | — | User-provided title for the bug report |
| `input_type` | `text` (enum) | No | — | Source type — see enum values below |
| `raw_input` | `text` | No | — | The full raw bug report text as submitted |
| `github_url` | `text` | Yes | NULL | GitHub issue URL (when `input_type = 'github_url'`) — fetched and merged into `raw_input` |
| `code_context` | `text` | Yes | NULL | Optional code snippet / context provided by user |
| `tags` | `text` | Yes | NULL | Comma-separated user-defined tags |
| `auto_tags` | `text` | Yes | NULL | JSON array of strings auto-generated by the Auto-Tagger agent (e.g. `["null-reference","async-race","auth"]`) |
| `project_id` | `integer` | Yes | NULL | Optional FK to `projects.id` |

**`input_type` enum values:**
- `raw_text` — plain English bug description
- `github_url` — GitHub issue URL (auto-fetched)
- `stack_trace` — stack trace / error output
- `jira_ticket` — Jira ticket description or URL
- `sentry_event` — Sentry error event (URL, ID, or details)
- `log_file` — log file output around the failure
- `curl_request` — failed curl command or API request/response
- `video_description` — description of a screen recording
- `screenshot` — description of a screenshot or visual bug
- `performance_profile` — performance profile or profiler output

#### Status

| Column | Type | Nullable | Default | Description |
|--------|------|----------|---------|-------------|
| `status` | `text` (enum) | No | `"pending"` | Pipeline status: `pending`, `running`, `completed`, `failed` |

#### Pipeline Outputs (set after pipeline completes)

All JSON fields store structured data as serialized strings. The frontend parses them with `JSON.parse()`.

| Column | Type | Nullable | Description |
|--------|------|----------|-------------|
| `confidence_score` | `real` | Yes | Deterministic confidence score stored as **0–1 decimal** (display requires `×100`) |
| `confidence_breakdown` | `text` | Yes | JSON: `{ score, rubric: Record<string,number>, missing: string[], evidence: string[], assumptions: string[] }` |
| `severity` | `text` (enum) | Yes | `"critical"` \| `"high"` \| `"medium"` \| `"low"` |
| `severity_reason` | `text` | Yes | One-sentence explanation of severity classification |
| `audit_trail` | `text` | Yes | JSON array of `AuditEntry` objects (see Pipeline doc) |
| `correlations` | `text` | Yes | JSON array of `CorrelationMatch` objects — cached after first fetch |
| `extracted_entities` | `text` | Yes | JSON: `EntityExtractionOutput` — component, trigger, environment, error messages, etc. |
| `hypotheses` | `text` | Yes | JSON array of `HypothesisItem` objects — ranked root-cause theories with retained/eliminated status |
| `reproduction_steps` | `text` | Yes | JSON: `StepValidationOutput` — prerequisites, numbered steps, expected/actual result, confidence rating |
| `test_code` | `text` | Yes | Raw test code string (Jest/TypeScript or other framework) |
| `flow_diagram` | `text` | Yes | Mermaid flowchart syntax string (generated deterministically from diagram schema) |
| `clarifying_questions` | `text` | Yes | JSON array of 5 question strings |
| `test_syntax_status` | `text` (enum) | Yes | `"verified"` \| `"warning"` \| `"unchecked"` — result of server-side syntax validation |
| `fix_suggestions` | `text` | Yes | JSON array of `FixSuggestion` objects — AI-generated ranked fix suggestions |

#### Resolution Tracking

| Column | Type | Nullable | Default | Description |
|--------|------|----------|---------|-------------|
| `resolution_status` | `text` (enum) | No | `"open"` | `"open"` \| `"in_progress"` \| `"fixed"` \| `"verified_fixed"` \| `"wont_fix"` |
| `resolved_by` | `text` | Yes | NULL | Name or identifier of the person who resolved it |
| `resolved_at` | `timestamp` | Yes | NULL | Timestamp when marked as resolved |
| `fix_description` | `text` | Yes | NULL | Free-text description of the fix applied |

#### Timestamps

| Column | Type | Nullable | Default | Description |
|--------|------|----------|---------|-------------|
| `created_at` | `timestamp` | No | `NOW()` | When the analysis was created |
| `updated_at` | `timestamp` | No | `NOW()` | When the analysis was last modified |

**Drizzle type**: `typeof analysesTable.$inferSelect` → exported as `Analysis`  
**Insert schema**: `insertAnalysisSchema` (auto-generated by `drizzle-zod`, omits `id`, `created_at`, `updated_at`)

## JSON Column Schemas

### `extracted_entities` (`EntityExtractionOutput`)

```typescript
{
  component: string;           // affected component or module
  triggerAction: string;       // user action that triggers the bug
  expectedBehavior: string;    // what should happen
  actualBehavior: string;      // what actually happens (the bug)
  environment: {
    os?: string;
    browser?: string;
    runtime?: string;
    version?: string;
    other?: string;
  };
  errorMessages: string[];     // list of error messages / codes found
  frequency: "always" | "intermittent" | "rare" | "unknown";
  additionalContext?: string;
}
```

### `hypotheses` (array of `HypothesisItem`)

```typescript
[{
  id: string;                        // unique ID within this analysis (e.g. "H1")
  title: string;                     // brief hypothesis name
  mechanism: string;                 // how this could cause the bug
  likelihood: "high" | "medium" | "low";
  confirmingEvidence: string[];      // evidence that supports this hypothesis
  refutingEvidence: string[];        // evidence that rules this out
  status: "retained" | "eliminated"; // AI's verdict after analysis
  statusReason: string;              // one-sentence explanation of verdict
}]
```

### `reproduction_steps` (`StepValidationOutput`)

```typescript
{
  prerequisites: string[];           // things needed before starting (installed packages, account state, etc.)
  steps: [{
    number: number;                  // step number starting at 1
    action: string;                  // exact action to perform
    expectedOutcome?: string;        // what should happen at this step
  }];
  expectedResult: string;            // overall expected result after all steps
  actualResult: string;              // what actually happens (the bug manifestation)
  environmentConfig: string[];       // specific environment settings needed
  validationNotes: string[];         // notes about edge cases or uncertainties
  confidenceRating: number;          // 1–10 scale for how confident the agent is
}
```

### `confidence_breakdown` (`ConfidenceBreakdown`)

```typescript
{
  score: number;                     // 0–100 (stored as 0–1 in confidence_score column)
  rubric: {                          // per-criterion scores
    environment: number;             // max 20
    frequency: number;               // max 15
    stack_trace: number;             // max 25
    expected_behavior: number;       // max 15
    similar_bug: number;             // max 20
    code_snippet: number;            // max 10
    reproduction_steps: number;      // max 15
  };
  missing: string[];                 // rubric criteria that scored 0 — shown as "what's missing"
  evidence: string[];                // LLM-provided evidence supporting the analysis
  assumptions: string[];             // LLM-provided assumptions due to incomplete data
}
```

### `fix_suggestions` (array of `FixSuggestion`)

```typescript
[{
  rank: number;               // 1 = most recommended
  title: string;              // brief fix name
  description: string;        // what to change and why
  codeLocation: string;       // specific function/class/file (e.g. "UserService.getProfile() in src/services/user.ts")
  effort: "low" | "medium" | "high";   // time estimate
  confidence: "high" | "medium" | "low";   // confidence this fixes the root cause
}]
```

### `audit_trail` (array of `AuditEntry`)

```typescript
[{
  timestamp: string;          // ISO 8601
  agent: string;              // agent name (e.g. "Entity Extraction", "Hypothesis Generator")
  action: string;             // machine-readable action identifier
  decision: string;           // human-readable summary of what the agent decided
  rationale: string;          // why it made this decision
  durationMs?: number;        // how long this agent took in milliseconds
  details?: [{                // optional structured detail rows (shown in timeline UI)
    label: string;
    value: string;
    status?: "ok" | "warn" | "info" | "error";
  }];
}]
```

### `correlations` (array of `CorrelationMatch`)

```typescript
[{
  id: number;                 // analysis ID of the similar bug
  title: string;              // title of the similar bug
  similarity: number;         // 0–100 similarity percentage
  commonFactors: string[];    // shared root cause elements
  rootCauseNote: string;      // how the historical bug's root cause relates
  createdAt: string;          // ISO 8601 creation time of the historical bug
}]
```

## Drizzle Client

```typescript
// lib/db/src/index.ts
import { drizzle } from "drizzle-orm/node-postgres";
import { Pool } from "pg";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
export const db = drizzle(pool, { schema });

// Usage in route handlers:
import { db, analysesTable } from "@workspace/db";
const analyses = await db.select().from(analysesTable).where(eq(analysesTable.id, 42));
```

## Schema Push vs Migrations

This project uses **push** mode (not migration files):

```bash
pnpm --filter @workspace/db run push
# Runs: drizzle-kit push --config ./drizzle.config.ts
```

This introspects the current DB and applies all changes needed to match the schema. It is safe for development but **not recommended for production** (use `drizzle-kit generate` + `drizzle-kit migrate` for production). In Replit, the push command is used for both dev and prod since the database is managed by Replit.
