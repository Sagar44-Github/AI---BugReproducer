# Features

This document explains each major feature end-to-end: what it does, how the data flows, where it's stored, and how it's displayed.

---

## Feature 1 — Confidence Scoring with Explainability

### What it does
Every pipeline run produces a structured confidence score (0–100) explaining *why* the analysis is reliable or unreliable.

### How it's different
The score is **deterministic** — computed by a rubric function, not generated by the LLM. This prevents hallucinated confidence values.

### Data flow
1. Before the pipeline runs, the route handler queries the DB for analyses with `status = "completed"` and checks keyword overlap with the current bug report (`hasSimilarBugs` flag)
2. During Agent 5 (Synthesizer), the LLM generates `confidenceEvidence[]` and `confidenceAssumptions[]`
3. After Agent 5, `calculateConfidenceScore()` runs the rubric using entity data + raw input + `hasSimilarBugs`
4. Result stored in `confidence_score` (0–1 decimal) and `confidence_breakdown` (JSON)

### Rubric weights
| Criterion | Max points | What earns it |
|-----------|-----------|---------------|
| Stack trace | 25 | Stack trace or exception trace present |
| Environment | 20 | OS, browser, runtime, or version specified |
| Similar bug | 20 | Similar bug found in historical DB |
| Frequency | 15 | Reproduction frequency known |
| Expected behavior | 15 | Expected outcome clearly stated |
| Reproduction steps | 15 | User-provided numbered steps |
| Code snippet | 10 | Code context attached |
| **Total (capped)** | **100** | |

### Storage
- `analyses.confidence_score`: `real` (0–1)
- `analyses.confidence_breakdown`: JSON string with full rubric breakdown, evidence, assumptions, and missing criteria

### Display
- **Detail page Overview tab**: Donut chart showing score breakdown, collapsible evidence/assumptions panel, "what's missing" list
- **History page**: Confidence column as a numeric percentage
- **Export page**: Header line "X% confidence"

## Feature 2 — Multi-Bug Correlation Engine

### What it does
Compares the target bug against all completed analyses in the database and finds semantically similar ones.

### How it works
1. Frontend calls `GET /api/analyses/:id/correlations` (or clicks "Find Similar" in the Similar Bugs tab)
2. Route handler fetches up to 50 completed analyses, extracts their `extractedEntities` + `tags`
3. Sends target + candidates to `runCorrelation()` — the LLM compares them and identifies structural matches
4. Results include: similarity % (0–100), common factors, and a note about how the historical root cause relates
5. Results are cached in `analyses.correlations` JSON column (subsequent calls return the cache)
6. "Refresh" button clears the cache by passing `?refresh=true`

### What makes a match
Only genuine structural matches are flagged — the LLM is instructed to avoid superficial keyword overlap. Common factors must be shared mechanisms (e.g. "JWT token expiry race condition") not just shared words.

### Storage
`analyses.correlations`: JSON array of `CorrelationMatch` objects, cached after first AI call

### Display
**Detail page "Similar Bugs" tab**:
- Similarity % badge (green ≥ 70%, yellow ≥ 40%, grey < 40%)
- Common factors tags
- "Root cause note" explaining the historical connection
- Link to the similar analysis
- "Refresh" button

## Feature 3 — Environment Diff Detector

### What it does
Compares two environment configurations (key=value pairs or JSON) and uses AI to classify each difference by relevance to a specific bug.

### Classification levels
| Level | Meaning |
|-------|---------|
| `critical` | This difference likely causes or contributes to the bug |
| `likely` | This difference may interact with the bug |
| `unlikely` | Probably not related but worth noting |
| `irrelevant` | No connection to this bug |

### Data flow
1. User fills in two env configs + a bug description at `/tools/env-diff`
2. Frontend calls `POST /api/tools/env-diff`
3. Route calls `runEnvDiff()` which sends everything to the LLM
4. LLM returns structured JSON with per-difference classification
5. Frontend displays sorted by criticality (critical first)

### Not persisted
Tool results are not stored in the database — they're ephemeral, session-based.

## Feature 4 — Reproduction Session Collaboration

### What it does
Multiple developers can annotate a bug's reproduction steps in real-time. Annotations are broadcast to all connected team members instantly via SSE.

### Annotation types
| Type | Meaning |
|------|---------|
| `note` | General comment |
| `verified` | Confirmed this step works as described |
| `failed` | This step doesn't reproduce the bug for them |
| `question` | A question about this step |

### Real-time mechanism
1. Each user on the Team tab opens a persistent SSE connection to `GET /api/analyses/:id/collaborate`
2. The server maintains an in-memory `Map<analysisId, Set<Response>>` — one set of SSE clients per analysis
3. When any user posts an annotation via `POST /api/analyses/:id/annotations`, the route broadcasts to all connected clients
4. The frontend appends the new annotation immediately without re-fetching

### Live collaborator count
The number of active SSE connections is counted and shown as "X collaborator(s) online".

### Limitations
- SSE client registry is **in-memory** — not persisted across server restarts
- Annotations themselves are stored in the `collaboration_annotations` table (persistent)

### Display
**Detail page "Team" tab**:
- Live collaborator count with pulsing indicator
- Chronological annotation feed with author, type badge, content, and step reference
- Add annotation form (author name, type dropdown, optional step ref, content)

## Feature 5 — NL2Test (Natural Language to Test Case)

### What it does
Converts a plain English test description into complete, runnable test code in any of 9 frameworks.

### Supported frameworks
Jest/TS · Jest/JS · Vitest · Mocha+Chai · Pytest · Cypress · Playwright · RSpec · JUnit

### Data flow
1. User describes the test in plain English at `/tools/nl2test`
2. Optionally provides existing code context
3. Frontend calls `POST /api/tools/nl2test`
4. Route calls `runNl2Test(description, framework, codeContext)`
5. LLM generates complete runnable test with proper imports/setup
6. Returns: `testCode`, `framework`, `explanation`, `coverageNotes`

## Feature 6 — Flaky Test Detector

### What it does
Analyzes test code and identifies which tests are likely to be flaky, why, and how to fix them.

### Root cause categories
| Category | Description |
|----------|-------------|
| `race_condition` | Tests race between async operations |
| `environment_dependency` | Test depends on specific OS, timezone, locale |
| `non_deterministic_data` | Uses random data, UUIDs, or timestamps without seeding |
| `timing` | Relies on `setTimeout` or fixed delays |
| `external_dependency` | Hits real network, DB, or file system |
| `state_leak` | Shared global state not cleaned between tests |
| `other` | Doesn't fit the above categories |

### Data flow
1. User pastes test code at `/tools/flaky-detector` and selects language
2. Frontend calls `POST /api/tools/flaky-detector`
3. Route calls `runFlakyDetector(testCode, language)`
4. LLM returns per-test analysis with risk level, category, explanation, and fix suggestion
5. Frontend displays overall risk badge + per-test cards sorted by risk level

## Feature 7 — Bug Severity Classifier

### What it does
Every completed analysis is classified by severity (critical / high / medium / low) with a one-sentence rationale.

### How it's generated
The severity is produced by **Agent 5 (Synthesizer)** — it runs as part of the main pipeline at no extra latency. The Synthesizer's Zod schema requires both `severity` and `severityReason`.

### Classification guidance (from system prompt)
- `critical`: Data loss, security breach, crashes blocking all users, or compliance violation
- `high`: Feature completely broken for many users, no workaround
- `medium`: Feature degraded, workaround exists
- `low`: Minor visual issue, edge case affecting few users

### Storage
- `analyses.severity`: enum column (`critical | high | medium | low`)
- `analyses.severity_reason`: text column

### Display
Severity appears in:
- Detail page header (colored badge)
- History page (table column)
- Dashboard stats (breakdown in stats cards)
- Export page header
- Similar bugs cards

## Feature 8 — Reproduction Audit Trail

### What it does
Every agent logs a timestamped entry explaining what it decided and why. The complete trail is stored and rendered as an interactive timeline.

### What's logged per agent
| Agent | What's in the entry |
|-------|---------------------|
| Entity Extraction | Component name, trigger, environment detected, error message count |
| Hypothesis Generator | Retained vs. eliminated count, top hypothesis name |
| Step Validator | Step count, prerequisites, confidence rating, key step names |
| Test Writer | Framework, language, coverage areas, syntax validation result |
| Synthesizer | Diagram complexity, severity, confidence evidence, total duration |
| Fix Suggester | Number of suggestions, top suggestion title and location |

Each entry also has `durationMs` — how long that agent took.

### Storage
`analyses.audit_trail`: JSON array of `AuditEntry` objects

### Display
**Detail page "Audit Trail" tab**:
- Vertical timeline with one node per agent
- Each node: agent icon, timestamp, agent name, action, decision text
- Expandable detail section showing labeled rows (e.g. "Evidence 1: …", "Total duration: 47 s")
- Status indicators: green (ok), amber (warn), blue (info), red (error)

## Feature 9 — AI Fix Suggestions (Agent 6)

### What it does
After the 5-agent core pipeline, a dedicated Fix Suggester agent generates 3–5 concrete, actionable code fixes ranked by likelihood of resolving the root cause.

### Why it's separate
Fix suggestions are generated **after** the Synthesizer has all the context — component, retained hypotheses, validated steps, and severity. Running it last gives it the richest possible input.

### Fix suggestion structure
```
Rank 1: "Add null check before email validation"
  Description: "Check for null/undefined before accessing email.length in handleSubmit()"
  Code location: "handleSubmit() in src/pages/Login.tsx:47"
  Effort: low
  Confidence: high
```

### Failure resilience
If the Fix Suggester fails (timeout, validation failure), the pipeline **does not fail** — it continues and stores `fix_suggestions = "[]"`. The frontend gracefully handles missing fix suggestions by not rendering that section.

### Display
- **Export page**: "AI Fix Suggestions" section with numbered cards showing rank, title, description, code location, effort badge, and confidence indicator
- **Detail page Overview tab**: Summary of top suggestion (planned)

## Feature 10 — Auto-Tagging (Agent 7)

### What it does
After Agent 6, an Auto-Tagger agent generates 3–8 short taxonomy tags for the bug based on all available analysis data.

### Tag format
- Lowercase
- Hyphenated (e.g. `null-reference`, `async-race`, `memory-leak`)
- Max 30 characters per tag
- Max 10 tags stored

### Example tags
`null-reference` · `async-race` · `auth` · `jwt` · `database` · `memory-leak` · `api-timeout` · `ui-rendering` · `config-error` · `pagination`

### How they're used
- Displayed as badges in the analysis detail header and export page
- Searchable in the History page
- Used by Bug Digest to summarize patterns across many analyses
- Supplement user-defined tags (`analyses.tags`)

## Feature 11 — Regression Guard Tool

### What it does
Given a test, a code diff/patch, and a bug description — the AI predicts whether the test would have caught the regression.

### Verdicts
| Verdict | Meaning |
|---------|---------|
| `would_catch` | The test exercises the exact code path changed |
| `would_miss` | The test doesn't cover the changed code path |
| `uncertain` | Can't determine without running the code |

### Output
- Verdict + confidence level
- Reasoning paragraph
- Critical lines from the diff that the test exercises
- Missed scenarios not covered by the test
- Recommendation for improving the test

## Feature 12 — Bug Digest

### What it does
AI-generated summary of all bugs in a time period — executive-style summary for engineering team retrospectives or sprint reviews.

### Periods
`today` · `last_7_days` · `last_30_days` · `all_time`

### Output sections
- **Summary**: 2–3 sentence executive overview
- **Highlights**: Key callouts (e.g. "3 critical bugs this week")
- **Patterns**: Recurring themes and root cause clusters
- **Recommendations**: Actionable items for the engineering team
- **Top components**: Most affected system areas
- **Risk level**: Overall risk assessment for the period
- **Stats note**: Key numbers (X critical, Y resolved, etc.)

## Feature 13 — Multi-Environment Reproduction Matrix

### What it does
Given reproduction steps for a bug and 2+ environment configurations, the AI predicts whether the bug would reproduce in each environment.

### Use cases
- Confirming whether a production-only bug also reproduces in staging
- Identifying which specific environment variable or config version causes the bug
- Determining whether a bug is infrastructure-level or code-level

### Output
- Per-environment prediction (yes / no / likely / unlikely) with confidence
- Reasoning explaining what each environment differs in
- The specific config difference that matters
- "Isolation verdict" — what the matrix tells us about the root cause
- "Recommendation" — which environment to debug in and why

## Feature 14 — Screenshot / Visual Bug Analysis

### What it does
Analyzes a description of a screenshot or screen recording and extracts all bug-relevant information as structured data.

### Why description-based (not image upload)
The LLM used (Groq's Llama 3.3 70B) is a text model. Users describe what they see in the screenshot — the tool extracts error messages, UI state, and generates a structured bug report ready to submit as a new analysis.

### Output
- `extractedText`: All visible error messages, stack traces, codes
- `uiState`: What was visible in the UI at failure
- `visibleErrors`: Specific error messages or codes
- `suggestedBugReport`: Well-structured bug description ready for the pipeline
- `inputType`: Suggested input type for the generated report
- `confidence`: How confident the extraction is

## Feature 15 — Resolution Tracking

### What it does
Track the resolution lifecycle of every bug from discovery to verified fix.

### Resolution statuses
| Status | Meaning |
|--------|---------|
| `open` | Default — bug identified, not yet being fixed |
| `in_progress` | Being actively worked on |
| `fixed` | Fix implemented, not yet verified |
| `verified_fixed` | Fix confirmed to work |
| `wont_fix` | Intentionally not fixing (e.g. out of scope, by design) |

### Resolution fields
- `resolution_status`: Current status
- `resolved_by`: Name or identifier of resolver
- `resolved_at`: Timestamp (auto-set when status = `"fixed"` or `"verified_fixed"`)
- `fix_description`: Free-text description of what was done

### API
`POST /api/analyses/:id/resolve` with `{ resolutionStatus, resolvedBy, fixDescription }`
